# Codex 위임 프롬프트 — 현실 계측치 전환 (A안)

설계는 `games/soccer/realistic-scale.md` 에 있다. 이 파일은 그것을 Codex 에
넘기기 위한 프롬프트다.

이전에 있던 0~6단계 구현 프롬프트와 A~E 리뷰 수정 프롬프트는 모두 소진돼
지웠다. 필요하면 커밋 `f25f2f8` 에서 볼 수 있다.

## 쓰는 법

**한 번에 한 단계만 보낸다.** 단계가 끝나면 결과를 확인하고 다음 프롬프트를
새 세션으로 보낸다.

Codex 는 저장소의 `AGENTS.md` 를 자동으로 읽는다. 루트와 `games/soccer/`
양쪽에 있으므로 배포 규칙·좌표계·문서 규칙은 다시 적지 않는다.
**`git push` 금지만은 프롬프트에서도 반복한다** — 되돌릴 수 없는 동작이라
한 번의 누락이 그대로 사고가 된다.

`<공통 블록>` 을 모든 단계에 그대로 붙이고 `<task>` 만 갈아끼운다.

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| 1 | 물리 상수 현실화 + 그리기 분리 | 기구적 동작 |
| 2 | 카메라 줌인·공 추적 | 기구적 동작 |
| 3 | 이동 행동 (걷기~스프린트) | 속도 분포 |
| 4 | 수비 재설계 | 슛 성공률 |
| 5 | 재밸런싱 | 승률·득점 목표 |

**1~4단계에서 밸런스 목표를 맞추려 하지 않는다.** 1단계 직후 득점이
폭증하는 것이 정상이다(프로토타입 90분 37.5골). 밸런스는 5단계에서
한 번에 맞춘다. 이걸 지키지 않으면 매 단계마다 상수를 흔들다 끝난다.

## 전환 직전 상태 (기록용, 목표 아님)

`node tools/soccer-sim.js -n 200 --seed 1`, 커밋 `10bd4ae` 기준.
현실 전환이 이 수치를 버린다. **프롬프트에 넣지 않았다** — Codex 가
이걸 유지하려 들면 1~4단계가 진행되지 않는다.

| 난이도 | 승률 (95% CI) | 득점 | 실점 | 총득점 |
|---|---|---|---|---|
| 쉬움 | 83.5% (77.7~88.0) | 3.75 | 1.51 | 5.26 |
| 보통 | 51.5% (44.6~58.3) | 2.33 | 1.86 | 4.18 |
| 어려움 | 25.5% (20.0~32.0) | 2.19 | 3.33 | 5.52 |

전체 경기당 총 득점 4.99. 오프사이드 쉬움 0.00 / 보통 0.68 / 어려움 0.34.
세 난이도 모두 목표 충족 — A~E 리뷰 수정이 밸런스를 깨지 않았다.

## 공통 블록 (1~5단계 모두에 붙인다)

```xml
<action_safety>
git push 를 절대 하지 않는다. 원격 저장소에 어떤 것도 올리지 않는다.
브랜치를 만들어 올리는 것도 금지다 — 저장소가 Public 이라 작업 브랜치도
소스 공개에 해당한다. 로컬 커밋은 자유롭게 해도 된다.

변경 범위는 games/soccer/ 와 tools/ 로 한정한다.
루트 index.html 과 일빵-런처-확정안.html 은 외부 도구가 재생성하는
번들이므로 건드리지 않는다. assets/ 와 app-ads.txt 도 건드리지 않는다.

관련 없는 리팩터링, 이름 변경, 코드 정리를 하지 않는다.
파일을 지우기 전에 현재 코드에서 참조되는지 먼저 검색한다.
git reset --hard 같은 파괴적 명령을 쓰지 않는다.
</action_safety>

<scale_targets>
현실 계측치 목표. games/soccer/realistic-scale.md 「목표 수치」와 같다.
1m = 20단위. R_PLAYER 와 R_BALL 은 반지름이다 — 지름과 헷갈리지 않게
쓸 값을 그대로 적는다.

  상수            현재    목표     실세계
  R_PLAYER          26      6      반지름 0.30m → 지름 0.6m
  R_BALL            13      2.2    반지름 0.11m → 지름 0.22m
  P_MAX            470    190      9.5m/s = 34km/h
  P_ACCEL         2100    150      7.5m/s²
  P_FRICTION         8      4      무입력 감속률 4s⁻¹
  B_FRICTION      0.55   0.82      초당 속도 배율(잔디 저항)
  B_MAX           2000    800      40m/s = 144km/h
  TOUCH_V          430    120      6m/s, 몸에 맞고 튀는 속도
  PASS_V           950    340      17m/s = 61km/h
  SHOOT_V         1650    660      33m/s = 119km/h
  GOAL_H           330    146      7.32m 규정
  GK_REACH_MUL     1.4    6.0      도달 1.48~2.01m

GK_REACH_MUL 은 R_PLAYER × 배수 × (0.82~1.12) 로 쓰이므로
6 × 6.0 × (0.82~1.12) = 29.5~40.3단위 = 1.48~2.01m 가 된다.

그리기 최소 지름(물리 반경과 분리): 선수 18 CSS px, 공 8 CSS px.

행동 목표(3단계에서 만든다): 평균 이동 7~9km/h(현재 44.7),
걷는 시간 60~70%(현재 13%).
수비 목표(4단계): 슛 성공률 10~15%.

경기장 105×68m 와 페널티박스·골에어리어·센터서클·페널티마크는 이미
실측이므로 바꾸지 않는다.

경기 길이는 기본 10분, 선택지는 6분 / 10분 / 20분(A안).
목표 득점은 10분 경기 총 2~3골.

난이도 목표 승률 80/53/23% 는 유지한다.
기준 대진은 골목 FC 대 골목 FC — 능력치가 모두 62인 동일 기준 팀이다
(tools/soccer-sim.js 의 --home-team 0 --away-team 0 기본값).
팀이 다르면 이 승률 목표는 성립하지 않는다.

난이도 축은 현행을 유지한다. LEVELS 는 react / aimErr / gk 세 축이고
슛·패스 시도율은 공용 AI_ACTION_RATE = 0.88 이다. 난이도별 shoot 값은
없으며 이 전환에서 되살리지 않는다.

HUMAN_ASSIST = [0.35, 0.35, 0] 은 제거하지 않는다. 값 재튜닝은 허용하되
난이도에 대해 비증가여야 한다(쉬움 >= 보통 >= 어려움).
커밋 a33b1df 에서 단조 축으로 정리한 결과를 되돌리지 않는다.
</scale_targets>

<phase_discipline>
이번 단계의 완료 기준에만 맞춘다.
1~4단계에서는 밸런스 목표(승률·득점)를 맞추려고 상수를 흔들지 않는다.
측정값은 기록만 하고, 목표에서 벗어나 있어도 그대로 보고한다.
밸런스는 5단계에서 한 번에 맞춘다.
</phase_discipline>

<missing_context_gating>
저장소 사실을 짐작하지 않는다. 필요한 내용은 파일을 직접 읽어 확인한다.
설계 문서에 없는 것을 새로 설계하지 말고, 정말 빠져 있으면 무엇이
비어 있는지 명시한다.
</missing_context_gating>

<verification_loop>
코드만 읽고 "될 것" 이라고 판단하지 않는다.

1. node tools/soccer-sim.js --self-test 를 돌려 전 항목 통과를 확인한다.
   이번 단계가 깨뜨린 항목이 있으면 셀프테스트를 고치는 것이 아니라
   구현을 고친다. 단, 축척 변경으로 전제가 바뀐 항목은 갱신한다.
2. node tools/soccer-sim.js -n 200 으로 측정한다. 30경기는 95% 신뢰구간이
   ±18%p 라 판정에 쓸 수 없다.
3. python -m http.server 8899 로 실제 브라우저에서 플레이한다.
   데스크톱 가로와 모바일 세로(경기장 90° 회전)를 모두 확인한다.
   확인이 끝나면 서버 프로세스를 정리한다.
4. 자동 검증은 requestAnimationFrame 에 의존하지 않는다. 백그라운드 창에서
   초당 1회로 스로틀된다. step(1/60) 을 직접 반복 호출한다.

검사가 실패하면 그 상태로 보고하지 말고 고친 뒤 다시 검사한다.
</verification_loop>

<completeness_contract>
작업을 끝까지 해결하고 멈춘다. 처음 그럴듯한 답에서 멈추지 않는다.
구현이 설계 문서와 달라졌으면 같은 작업에서 문서를 갱신한다.
차이가 남은 상태로 완료를 선언하지 않는다.
</completeness_contract>

<default_follow_through_policy>
합리적인 저위험 해석을 골라 계속 진행한다. 루틴한 질문으로 멈추지 않는다.

다만 다음 경우에는 멈추고 물어본다.
- 이번 단계의 완료 기준을 3회 시도해도 맞추지 못할 때
- 설계 문서끼리 충돌할 때
- games/soccer/index.html 이 3000줄을 넘어 파일 분할이 필요해질 때
- 되돌리기 어려운 동작이 필요할 때
</default_follow_through_policy>

<grounding_rules>
모든 주장을 실제 실행 결과나 읽은 파일에 근거해서 말한다.
추론을 사실처럼 말하지 않는다. 가설이면 가설이라고 표시한다.
밸런스 수치는 짐작으로 확정하지 않는다. 측정 조건과 결과를 함께 적는다.
</grounding_rules>

<structured_output_contract>
끝나면 다음만 보고한다. 긴 서두나 반복 요약을 넣지 않는다.

1. 구현한 것 — 항목별 한 줄
2. 측정값 — 이번 단계의 완료 기준 항목. 밸런스 수치는 참고로만
3. 브라우저에서 확인한 것 / 확인하지 못한 것
4. 설계 문서에서 바꾼 부분
5. 남은 문제, 다음 단계로 넘긴 것
</structured_output_contract>

<progress_updates>
진행 보고는 짧게, 결과 중심으로. 주요 단계 전환이나 막힌 지점만 알린다.
</progress_updates>
```

## 1단계 — 물리 상수 현실화와 그리기 분리

```xml
<task>
저장소 ilbbangsite. 동네 축구를 현실 계측치로 바꾸는 1단계를 구현한다.

먼저 games/soccer/README.md 목차를 따라 realistic-scale.md 를 읽고,
principles.md 와 baseline.md 로 현재 상태를 확인한다.

할 일 1 — 물리 상수를 <scale_targets> 의 값으로 바꾼다.
  index.html 의 R_PLAYER, R_BALL, P_ACCEL, P_MAX, P_FRICTION,
  B_FRICTION, B_MAX, TOUCH_V, PASS_V, SHOOT_V, GOAL_H, GK_REACH_MUL.
  1m = 20단위 매핑을 유지한다. 경기장 치수는 이미 실측이니 건드리지 않는다.

할 일 2 — 그리기 반경을 물리 반경에서 분리한다.
  지금 R_PLAYER 하나가 충돌과 그리기를 겸한다. 0.6m 선수를 그대로 그리면
  화면에서 사라진다(105m 경기장을 360px 폰에 담으면 1.5px).

  물리는 R_PLAYER(6단위)를 쓰고, 그리기는 화면 최소 지름을 보장하는
  별도 값을 쓴다. drawPlayer / drawBall / drawMinimap 이 그리기 값을
  쓰게 하고, collide / separateAll / takePossession 등 물리 경로는
  물리 값을 그대로 쓰게 한다.

  resize() 의 MIN_PLAYER_PX 로 줌 하한을 잡던 방식은 없앤다. 줌은
  2단계에서 카메라가 정하고, 가독성은 그리기 크기가 책임진다.

할 일 3 — 경기 길이를 6분 / 10분 / 20분(360 / 600 / 1200초)으로 바꾸고
  기본을 600초로. 저장 설정(matchSec)의 유효값 검사와 마이그레이션을
  다음 매핑으로 구현한다. 유효한 값은 그대로 두고 없어진 값만 옮긴다.

      기존 180 → 360
      기존 360 → 360 유지
      기존 600 → 600 유지
      그 외·없음 → 600 (새 기본값)

  이 매핑을 검증하는 셀프테스트 항목을 추가한다.

주의: 이 단계 직후 득점이 폭증한다. 프로토타입에서 현실 상수만 바꾸면
90분 37.5골(실제 2.7골), 슛 성공률 78%가 나왔다. 선수가 작아져 몸으로
막던 수비가 사라지기 때문이다. 정상이며 4단계에서 해결한다.
<phase_discipline> 대로 여기서 밸런스를 맞추려 하지 않는다.

끝난 상태:
- 물리 상수가 목표값이고, 실제로 측정해 확인했다(직선 주행 거리로 속도,
  충돌 반경으로 크기).
- 브라우저에서 선수와 공이 보이고 조작이 된다. 카메라는 아직 전체를
  보여주므로 마커가 실제 크기보다 크게 그려지는 상태가 정상이다.
- 셀프테스트 통과. 축척 전제가 바뀌어 갱신한 항목은 이유를 보고한다.
- 200경기 측정값을 기록만 하고 보고한다(목표에 맞추지 않는다).
- realistic-scale.md 1단계 절을 구현 결과로 갱신한다.
</task>
```

## 2단계 — 카메라

```xml
<task>
저장소 ilbbangsite. 현실 계측치 전환 2단계, 카메라를 구현한다.
1단계(물리 상수·그리기 분리)가 끝난 상태를 전제로 한다.

games/soccer/realistic-scale.md 의 「2. 카메라」를 따른다.

할 일:
1. 공을 따라가며 줌인한다. 경기장 전체를 보여주지 않는다.
2. 가시 범위를 화면 크기가 아니라 논리 단위로 고정한다.
   가로 화면 40m, 세로 화면 26m(회전 후 짧은 축 기준).
   창이 커도 더 넓게 보이면 안 된다 — 큰 화면이 유리해져
   principles.md 2번(창 크기가 경기 결과를 바꾸지 않는다)을 어긴다.
3. 공의 진행 방향으로 최대 6m 앞을 미리 보여준다(카메라 리드).
   급격한 흔들림이 없도록 기존의 지수 보간을 유지한다.
4. 경기장 밖이 보이지 않게 가두는 현행 동작을 유지한다.
5. 미니맵을 항상 켠다. 전체가 보이는 경우가 없어지므로 view.whole 조건을
   없앤다. 미니맵이 유일한 전술 시야가 되므로 크기와 대비를 키우고,
   조작 중인 선수를 미니맵에서 구분할 수 있게 한다.

주의: 세로 화면에서 경기장을 90° 돌린다. 그리기만 돌리면 안 되고 입력
벡터도 같은 각도로 돌려야 한다. 회전 변환의 translate 는 회전 전
좌표계에 적용되므로 필드 순서 (x, y) 를 그대로 쓴다. 과거에 뒤집어 써서
경기장이 화면 폭의 63%만 채우는 버그가 있었다.

끝난 상태:
- 데스크톱과 모바일 세로에서 실제로 플레이해 공을 따라가는지 확인했다.
- 창 크기를 여러 개로 바꿔도 가시 범위가 논리 단위로 동일하다.
  이를 검증하는 셀프테스트 항목을 추가한다.
- 미니맵으로 팀 대형과 빈 공간을 읽을 수 있다.
- 선수와 공이 모든 화면 크기에서 읽힌다.
- realistic-scale.md 2단계 절을 구현 결과로 갱신한다.
</task>
```

```xml
저장소 ilbbangsite. 현실 계측치 전환 3단계, 이동 행동을 구현한다.
2단계(카메라)가 끝난 상태를 전제로 한다.

games/soccer/realistic-scale.md 의 「3. 이동 행동」과
games/soccer/movement-metrics.md 의 계측 정의를 따른다.

문제: 최고속도를 34km/h 로 묶어도 프로토타입 평균이 17km/h 였다.
실제 프로는 7km/h 다. AI 가 항상 전속으로 달리기 때문이다.
현실적인 페이스는 속도 상한이 아니라 행동 모델에서 나온다.

할 일:
1. 목표 속도를 상황에서 정한다.
     걷기     5km/h   공이 멀고 위치를 지킬 때
     조깅    11km/h   대형 이동, 복귀
     달리기  20km/h   압박, 추격
     스프린트 34km/h  공 경합, 침투
   aiPlayer() 가 목표 지점만 정하고 항상 전속으로 가는 구조를 바꿔,
   목표까지의 거리와 역할·상황으로 목표 속도를 함께 정한다.
2. 사람 입력의 스틱 크기를 그대로 속도로 쓴다(아날로그).
   키보드는 이진이므로 걷기 수정키를 둔다. 키 배치는 기존 조작과
   충돌하지 않게 고르고 화면 안내(HOWTO)를 갱신한다.
3. 체력(stamina)이 스프린트를 실제로 제약하게 한다.
   지금은 사람 조작 선수만 소모한다. AI 도 소모하게 하고, 후반에
   페이스가 떨어지는 것이 측정에서 보이게 한다.
   체력은 경기 시작에만 초기화한다 — 킥오프마다 회복시키지 않는다.

끝난 상태:
- 난이도마다 200경기 측정에서 평균 이동 7~9km/h, 걷는 시간 60~70%,
  최고 34km/h 이하. 표본·속도 구간·집계식은 movement-metrics.md 그대로다.
- 후반 평균 속도가 전반보다 낮다(체력 효과). 수치로 보고한다.
- 브라우저에서 걷기·조깅·달리기·스프린트가 눈으로 구분된다.
- 측정 도구가 속도 분포를 출력하도록 확장한다(구간별 비율).
- realistic-scale.md 3단계 절을 구현 결과로 갱신한다.
</task>
```

## 4단계 — 수비 재설계

```xml
<task>
저장소 ilbbangsite. 현실 계측치 전환 4단계, 수비를 재설계한다.
3단계(이동 행동)가 끝난 상태를 전제로 한다.
이 전환에서 가장 큰 작업이다.

games/soccer/realistic-scale.md 의 「4. 수비 재설계」를 따른다.

문제: 선수 지름을 2.6m → 0.6m 로 줄이면 슛 성공률이 78%가 된다
(실제 11%). 지금까지 수비의 대부분을 선수 몸집이 하고 있었다.
경기장이 텅 비어 막을 몸이 없다. 몸집으로 막던 것을 위치와 판단으로
대체해야 한다.

할 일 0 — 먼저 통계 집계를 고친다. 이걸 안 하면 완료 판정이 성립하지 않는다.

  슛 성공률 = 슛에서 비롯된 득점 / 슛 시도, 로 정의한다.

  지금은 측정할 수 없다. matchStats.shots 집계가 3곳(세트피스,
  kickOwned, collide)뿐이라 드리블 골인·굴절·자책·패스 득점이 슛에
  잡히지 않는다. 그래서 프로토타입에서 10분 득점 4.5 > 슛 4.2 가 나왔다.

  - 모든 득점을 '슛 득점' 또는 '비슛 득점' 중 하나로 분류해 집계한다.
  - 득점 = 슛 득점 + 비슛 득점 항등식이 성립함을 셀프테스트로 검증한다.
  - 측정 도구가 슛 성공률과 비슛 득점 비율을 함께 출력하게 한다.
  - 그 다음에 아래 수비 작업을 하고 성공률을 측정한다.

할 일:
1. 마킹 — 수비수가 가까운 상대 공격수를 맡아 골문 쪽 라인에 선다.
   전원이 공만 쫓아 뭉치지 않게 기존 슬롯 개념과 함께 쓴다.
2. 패스 레인 차단 — passTarget() 의 laneRisk 계산을 수비 측에서도 써서,
   수비수가 위험한 패스 레인 위에 서게 한다. 공격이 쓰는 것과 같은
   함수를 쓰면 두 판단이 일관된다.
3. 슛 블록 — 슈터와 골문 사이에 몸을 넣는다. 선수가 작아진 만큼
   의도적으로 서야 막힌다.
4. 태클 거리 재조정 — 지금 92단위(4.6m)는 새 크기에서 너무 멀다.
   선수 지름 0.6m 기준으로 다시 잡는다.

이 단계의 판정 지표는 승률이 아니라 슛 성공률이다. 목표는 10~15%.
승률과 득점은 5단계에서 맞춘다.

끝난 상태:
- 득점 = 슛 득점 + 비슛 득점 항등식이 셀프테스트로 검증된다.
- 200경기 측정에서 슛 성공률 10~15%.
- 비슛 득점 비율을 수치로 보고한다(실제 축구에서도 굴절·자책이 있으므로
  0이어야 하는 것은 아니다. 다만 절반을 넘으면 설계가 잘못된 것이다).
- 경기당 슛 수가 실제 축구 비율에 가깝다(90분 환산 20~30개).
- 브라우저에서 수비가 몸을 던져 막는 장면이 실제로 보인다.
- 전술 슬라이더(수비선·압박·폭·추격 인원)가 여전히 의미 있게 작동한다.
  team-tactics.md 의 상성이 유지되는지 확인하고, 깨졌으면 보고한다.
- realistic-scale.md 4단계 절을 구현 결과로 갱신한다.
</task>
```

## 단계가 끝날 때마다

Codex 보고를 받으면 다음을 직접 확인한다.

1. `git status -sb` — `ahead` 만 있고 push 흔적이 없는지
2. `node tools/soccer-sim.js --self-test` — 전 항목 통과
3. 보고된 측정값이 재현되는지 (직접 같은 명령 실행)
4. 브라우저에서 직접 플레이 — "확인했다" 를 그대로 믿지 않는다
5. `wc -l games/soccer/*.md` — 설계 문서 200줄 제한

1~4단계에서 밸런스 수치가 목표를 벗어나 있는 것은 정상이다.
그걸 이유로 되돌리지 않는다.
