# Codex 위임 프롬프트

동네 축구 구현을 Codex 에 맡길 때 쓰는 프롬프트 모음.

## 쓰는 법

**한 번에 한 단계만 보낸다.** 6단계를 한 프롬프트에 몰아넣으면 Codex 가
앞 단계를 대충 끝내고 넘어간다. 단계가 끝나면 결과를 확인하고 다음
프롬프트를 새 세션으로 보낸다.

Codex 는 저장소의 `AGENTS.md` 를 자동으로 읽는다. 루트와 `games/soccer/`
양쪽에 있으므로 배포 규칙·좌표계·문서 규칙은 프롬프트에 다시 적지 않아도
된다. **단 `git push` 금지만은 프롬프트에서도 반복한다** — 되돌릴 수 없는
동작이라 한 번의 누락이 그대로 사고가 된다.

아래 `<공통 블록>` 은 모든 단계에 그대로 붙인다. `<task>` 만 갈아끼운다.

## 공통 블록 (모든 프롬프트에 붙인다)

```xml
<action_safety>
git push 를 절대 하지 않는다. 원격 저장소에 어떤 것도 올리지 않는다.
브랜치를 만들어 올리는 것도 금지다 — 저장소가 Public 이라 작업 브랜치도
소스 공개에 해당한다. 로컬 커밋은 자유롭게 해도 된다.

변경 범위는 games/soccer/ 와 tools/ 로 한정한다.
루트 index.html 과 일빵-런처-확정안.html 은 외부 도구가 재생성하는
번들이므로 건드리지 않는다. assets/ 와 app-ads.txt 도 건드리지 않는다.

관련 없는 리팩터링, 이름 변경, 코드 정리를 하지 않는다.
파일을 지우기 전에 현재 코드에서 참조되는지 먼저 검색한다.
git reset --hard 같은 파괴적 명령을 쓰지 않는다.
</action_safety>

<missing_context_gating>
저장소 사실을 짐작하지 않는다. 필요한 내용은 파일을 직접 읽어 확인한다.
설계 문서에 없는 것을 새로 설계하지 말고, 정말 빠져 있으면 무엇이
비어 있는지 명시한다.
</missing_context_gating>

<verification_loop>
코드만 읽고 "될 것" 이라고 판단하지 않는다.

1. node tools/soccer-sim.js -n 200 을 돌려 승률과 경기당 득점을 확인한다.
   목표는 쉬움 80% / 보통 53% / 어려움 23%, 경기당 총 득점 5~6골.
   30경기는 95% 신뢰구간이 ±18%p 라 판정에 쓸 수 없다. 반드시 200 이상.
2. python -m http.server 8899 를 띄우고 실제 브라우저에서 플레이한다.
   데스크톱 가로와 모바일 세로(경기장 90° 회전)를 모두 확인한다.
   확인이 끝나면 서버 프로세스를 정리한다.
3. 자동 검증은 requestAnimationFrame 에 의존하지 않는다. 백그라운드 창에서
   초당 1회로 스로틀된다. step(1/60) 을 직접 반복 호출한다.

검사가 실패하면 그 상태로 보고하지 말고 고친 뒤 다시 검사한다.
</verification_loop>

<completeness_contract>
작업을 끝까지 해결하고 멈춘다. 처음 그럴듯한 답에서 멈추지 않는다.
구현이 설계 문서와 달라졌으면 같은 작업에서 문서를 갱신한다.
차이가 남은 상태로 완료를 선언하지 않는다.
</completeness_contract>

<default_follow_through_policy>
합리적인 저위험 해석을 골라 계속 진행한다. 루틴한 질문으로 멈추지 않는다.

다만 다음 경우에는 멈추고 물어본다.
- 밸런스를 3회 조정해도 목표 범위에 들어오지 않을 때
- 설계 문서끼리 충돌할 때
- games/soccer/index.html 이 3000줄을 넘어 파일 분할이 필요해질 때
- 되돌리기 어려운 동작이 필요할 때
</default_follow_through_policy>

<grounding_rules>
모든 주장을 실제 실행 결과나 읽은 파일에 근거해서 말한다.
추론을 사실처럼 말하지 않는다. 가설이면 가설이라고 표시한다.
밸런스 수치는 짐작으로 확정하지 않는다. 측정 조건과 결과를 함께 적는다.
</grounding_rules>

<structured_output_contract>
끝나면 다음만 보고한다. 긴 서두나 반복 요약을 넣지 않는다.

1. 구현한 것 — 항목별 한 줄
2. tools/soccer-sim.js -n 200 결과 표 (승률, 신뢰구간, 경기당 총 득점)
3. 브라우저에서 확인한 것 / 확인하지 못한 것
4. 설계 문서에서 바꾼 부분
5. 남은 문제, 다음 단계로 넘긴 것
</structured_output_contract>

<progress_updates>
진행 보고는 짧게, 결과 중심으로. 주요 단계 전환이나 막힌 지점만 알린다.
</progress_updates>
```

## 0단계 — speed 스윕 측정 (1단계 전에 한 번)

```xml
<task>
저장소 ilbbangsite. tools/soccer-sim.js 에 speed 스윕 기능을 추가하고
기준선을 측정한다.

먼저 games/soccer/README.md 의 목차를 따라 balance.md 와 principles.md 를
읽는다.

할 일:
1. tools/soccer-sim.js 에 --sweep-speed 옵션을 추가한다.
   LEVELS[1].speed 를 0.84~0.94 까지 0.01 간격으로 바꿔가며 각 200경기를
   돌려 승률 곡선을 낸다. 시드는 고정한다.
2. 결과를 games/soccer/balance.md 「계획된 측정」 절에 표로 기록하고,
   측정 조건(명령·시드·경기 수·날짜)을 함께 적는다.

목적: speed 가 0.87 근처에서 계단 함수처럼 작동한다는 기존 관찰이 지금도
유효한지 확인하는 것이다. 1단계 구현 후 같은 스윕을 돌려 비교할 기준선이
된다. 이 결과가 「난이도와 팀 강함의 축 분리」 결정에 직접 들어간다.

끝난 상태: 승률 곡선이 balance.md 에 기록되고, 계단이 있는지 없는지에
대한 판단이 근거와 함께 적혀 있다.
</task>
```

*(공통 블록에서 `verification_loop` 의 2번 브라우저 항목은 이 단계에
해당 없음 — 코드 변경이 도구에만 있다.)*

## 1단계 — 조작·플레이 감

```xml
<task>
저장소 ilbbangsite. 동네 축구 게임의 1단계(조작·플레이 감)를 구현한다.
작업 대상은 games/soccer/index.html 한 파일이다.

먼저 games/soccer/README.md 를 읽고 목차를 따라 principles.md, baseline.md,
input-system.md, balance.md, roadmap.md 를 읽는다.
설계는 이미 확정돼 있다. 새로 설계하지 말고 input-system.md 에 적힌 것을
구현한다.

구현 항목 6개:
1. 공 소유 상태 — ball.owner 를 살린다(현재 선언만 되고 쓰이지 않는다).
   선수 반경 안에 공이 들어오고 상대 속도가 낮으면 트래핑.
   소유 중 최고속도 ×0.88, 재소유 쿨다운 0.35초.
2. 조준 — 슛·패스 방향을 스틱/키 입력 방향으로 정한다.
   입력이 없으면 기존 aimAt() 자동 조준으로 폴백한다.
   세로 화면에서 입력 벡터 회전이 조준에도 적용되는지 반드시 확인한다.
3. 액션 4개 — 슛(파워 충전), 짧은 패스, 스루패스, 태클.
   passTarget() 이 상대 위치를 보지 않아 수비수 정면으로 패스하는 문제를
   함께 고친다.
4. 모바일 버튼 — 공 소유 여부로 버튼 2개의 의미와 라벨을 바꾼다.
   소유 중 [슛][패스], 비소유 [태클][선수전환].
5. 수동 선수 전환 — 공 기준 가까운 순서로 순환. 수동 전환 직후 약 1.2초는
   자동 전환(pickControlled)을 막는다.
6. 스프린트 — 속도 ×1.25. 체력 소모는 이번 단계에서 0으로 둔다
   (3분 경기에서 유의미한지 미정. input-system.md 참조).

주의: collide() 를 전면 재작성하게 된다. 공 경합 방식이 바뀌므로
balance.md 의 기존 수치는 전부 무효가 된다. 재측정이 필수다.

끝난 상태:
- node tools/soccer-sim.js -n 200 이 목표 범위 안
  (쉬움 80% / 보통 53% / 어려움 23%, 경기당 총 5~6골)
- 브라우저에서 6개 항목이 모두 실제로 동작
- 구현이 input-system.md 와 달라진 부분은 문서를 갱신
- balance.md 에 1단계 후 측정 결과를 조건과 함께 추가
</task>
```

## 2단계 — 경기 규칙 (아웃·세트피스·전후반)

```xml
<task>
저장소 ilbbangsite. 동네 축구 게임의 2단계를 구현한다.
1단계(조작)가 끝난 상태를 전제로 한다.

games/soccer/README.md 목차를 따라 match-rules.md 를 중심으로 읽는다.

구현 항목:
1. 아웃오브플레이 — 터치라인 벽 반사를 제거하고 스로인/골킥/코너킥으로
   재개한다. collide() 에서 ball.lastTouch 를 기록한다.
2. 세트피스 상태 기계 — state 에 'setpiece' 를 추가하고 스로인·골킥·
   코너킥·프리킥·킥오프를 하나의 흐름으로 처리한다.
   resetPositions() 를 킥오프 전용에서 세트피스 배치 함수로 일반화한다.
   대기 시간은 match-rules.md 의 표를 따른다.
3. 전·후반제 — 90초 × 2, 하프타임에 코트 체인지.
   side===0 을 방향으로 쓰는 코드(homePos, aimAt, gkTarget, passTarget,
   색상 배정)를 팀별 attackDir 필드로 걷어낸다.
4. 경기 길이 설정 3분 / 6분 / 10분, 기본 3분.
5. 추가시간 — 세트피스로 멈춘 시간을 누적해 각 반 끝에 더한다.

오프사이드와 파울은 이 단계에 넣지 않는다. 3단계다.

끝난 상태:
- 아웃 판정 후 재개까지 흐름이 끊긴 느낌이 없다
- 세트피스에서 선수가 겹치거나 경기장 밖으로 나가지 않는다
- 코트 체인지 후 양 팀이 올바른 골문을 공격한다
- 밸런스 재측정 결과가 목표 범위 안
</task>
```

<task>

1. 오프사이드 — 패스를 차는 순간 판정. 난이도 연동(쉬움=끄기,

레드카드(퇴장)는 넣지 않는다. 인원 가변 처리라 4단계 포메이션 테이블화
이후로 미뤘다.

끝난 상태:
- 오프사이드 판정이 경기당 3회 이하
- 판정 이유가 화면에서 보인다
- 밸런스 재측정 결과가 목표 범위 안
</task>

## 4단계 — 팀·전술

```xml
<task>
저장소 ilbbangsite. 동네 축구 게임의 4단계를 구현한다.

games/soccer/team-tactics.md 를 따른다. balance.md 의 speed 스윕 결과를
먼저 확인한다 — 「난이도와 팀 강함의 축 분리」 결정이 그 데이터에 달려
있다. 계단이 남아 있으면 속도를 팀 능력치로 옮기는 순간 팀 강함도 계단이
된다. 판단 근거를 보고에 포함한다.

구현 항목:
1. 선수 능력치 5개 (속도·슛·패스·수비·체력) + 골키퍼 선방.
   값은 1~99, 화면에는 5단계 막대로만 표시한다.
2. 포메이션 테이블화 — 4-4-2 / 4-3-3 / 3-5-2 / 5-3-2.
3. 전술 슬라이더 — slotTarget() 의 상수를 노출한다.
   수비 라인 높이, 압박 강도, 폭, 추격 인원.
4. 팀 8~12개. 종합 등급은 선수 능력치에서 파생시킨다(직접 입력 금지).
5. 상성 — 별도 보정 계수를 곱하지 않는다. 기존 물리로 자연히 발생해야
   한다. 발생하지 않으면 상수 범위를 조정한다.

목표 승률은 평균 등급의 기준 팀끼리 붙었을 때로 재정의한다.

끝난 상태:
- 팀 등급차가 승률에 단조 반영된다
- 전술 조합별 봇 대 봇 승률 행렬에서 가위바위보가 관찰된다
- 능력치를 전부 동일하게 두면 이전 밸런스가 재현된다(회귀 확인)
- 측정 결과를 balance.md 에 기록
</task>
```

## 6단계 — 리그·시즌·기록
