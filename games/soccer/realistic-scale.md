# 현실 계측치 전환

**상태: 계획.** 측정으로 근거를 잡았고 구현은 시작하지 않았다.

경기장·선수·공·속도를 실제 축구 계측치로 맞추고, 카메라를 줌인해 공을
따라가게 한다. 지금은 경기장 선만 실측이고 그 위의 모든 것이 과장돼 있다.

## 왜 상수 교체로 끝나지 않는가

현실 상수로 바꿔 200경기를 돌린 결과(`tmp` 프로토타입, 2026-08-01):

| | 득점 | 슛 | 유효 | 평균속도 | 걷기 |
|---|---|---|---|---|---|
| 현재 3분 | 4.00 | 14.1 | 7.0 | 44.7km/h | 13% |
| 현실 10분 | 4.50 | 4.2 | 3.0 | 17.2km/h | 22% |
| 현실 90분 | **37.50** | 48.3 | 32.8 | 18.1km/h | 18% |
| 실제 프로 90분 | 2.7 | 25 | 8 | 7km/h | 70% |

**발견 1 — 수비의 대부분을 선수 몸집이 하고 있었다.**
선수 지름을 2.6m → 0.6m 로 줄이면 슛 성공률이 78%가 된다(실제 11%).
막을 몸이 사라지기 때문이다. 현실화는 수비 로직을 새로 만드는 일이다.

**발견 2 — 속도 상한만으로는 현실적인 페이스가 안 나온다.**
최고속도를 34km/h 로 묶어도 평균이 17km/h 다. AI 가 항상 전속으로
달리기 때문이다. 현실감은 상한이 아니라 행동 모델에서 나온다.

## 목표 수치

**`R_PLAYER`·`R_BALL` 은 반지름이다.** 2배 오류를 막으려고 쓸 값을 그대로
적었다. 아래는 프로토타입으로 돌려 물리 동작을 확인한 값이다(2026-08-01).

| 상수 | 현재 | 목표 | 실세계 |
|---|---|---|---|
| `R_PLAYER` | 26 | **6** | 반지름 0.30m → 지름 0.6m (현재 2.6m) |
| `R_BALL` | 13 | **2.2** | 반지름 0.11m → 지름 0.22m (현재 1.30m) |
| `P_MAX` | 470 | **190** | 9.5m/s = 34km/h (현재 84.6) |
| `P_ACCEL` | 2100 | **150** | 7.5m/s² (현재 105) |
| `P_FRICTION` | 8 | **4** | 무입력 감속률 4s⁻¹ |
| `B_FRICTION` | 0.55 | **0.82** | 초당 속도 배율(잔디 저항) |
| `B_MAX` | 2000 | **800** | 40m/s = 144km/h |
| `TOUCH_V` | 430 | **120** | 6m/s, 몸에 맞고 튀는 속도 |
| `PASS_V` | 950 | **340** | 17m/s = 61km/h |
| `SHOOT_V` | 1650 | **660** | 33m/s = 119km/h (현재 297) |
| `GOAL_H` | 330 | **146** | 7.32m 규정 (현재 16.5m) |
| `GK_REACH_MUL` | 1.4 | **6.0** | 도달 1.48~2.01m (현재 0.91m) |

`GK_REACH_MUL` 은 `R_PLAYER × 배수 × (0.82~1.12)` 로 쓰인다 —
`6 × 6.0 × (0.82~1.12) = 29.5~40.3단위 = 1.48~2.01m`.

행동 목표는 상수가 아니라 3단계에서 만든다: **평균 이동 7~9km/h**
(현재 44.7), **걷는 시간 60~70%**(현재 13%).
표본 범위와 속도 구간은 `movement-metrics.md` 정의를 따른다.

경기장(105×68m)·페널티박스·센터서클은 이미 실측이라 그대로 둔다.

### 그리기 최소 크기

물리 반경과 분리해 화면 최소 **지름**을 보장한다 — 선수 **18 CSS px**,
공 **8 CSS px**.

가로 40m·1280px 화면이면 32px/m 라 선수 0.6m = 19px 로 하한을 겨우 넘고,
360px 폰·세로 26m 에서는 13.8px/m 라 8.3px 가 되어 하한이 작동한다
(약 2.2배 확대). 이게 분리가 필요한 이유다.

## 단계

### 1. 물리 상수와 그리기 분리

상수를 목표값으로 바꾸고, **그리기 반경을 물리 반경에서 떼어낸다.**
지금은 `R_PLAYER` 하나가 충돌과 그리기를 겸한다. 0.6m 선수를 그대로
그리면 화면에서 사라진다.

```
R_PLAYER      물리 전용 (6단위 = 0.6m)
DRAW_R_MIN_PX 화면 최소 지름 (CSS px). 줌과 무관하게 보장
```

`MIN_PLAYER_PX` 로 줌 하한을 잡던 방식(`resize()`)은 없앤다. 줌은
카메라가 정하고, 가독성은 그리기 크기가 책임진다.

### 2. 카메라

공을 따라가며 줌인한다. **가시 범위를 화면 크기가 아니라 논리 단위로
고정한다** — 창이 커도 더 넓게 보이지 않게 한다. 그러지 않으면 큰
화면이 유리해져 `principles.md` 2번을 어긴다.

| 항목 | 값(제안) |
|---|---|
| 가시 범위 | 가로 **40m** (경기장의 38%) |
| 세로 화면 | 가로 26m — 회전 후 짧은 축 기준 |
| 추종 | 공 위치 + 진행 방향 리드 최대 6m |
| 경계 | 경기장 밖이 보이지 않게 가둠 (현행 유지) |

미니맵은 **항상 켠다.** 전체가 보이는 경우가 없어지므로 `view.whole`
조건을 없앤다. 미니맵이 유일한 전술 시야가 되므로 크기와 대비를 키운다.

### 3. 이동 행동 (걷기·조깅·달리기·스프린트)

속도 상한만 바꾸면 전원이 34km/h 로 달린다. 목표 속도를 상황에서 정한다.

| 상태 | 속도 | 언제 |
|---|---|---|
| 걷기 | 5km/h | 공이 멀고 위치를 지킬 때 |
| 조깅 | 11km/h | 대형 이동, 복귀 |
| 달리기 | 20km/h | 압박, 추격 |
| 스프린트 | 34km/h | 공 경합, 침투. 체력 소모 |

`aiPlayer()` 가 목표 지점만 정하고 항상 전속으로 가는 구조를 바꿔,
목표까지의 거리와 역할·상황으로 목표 속도를 함께 정한다.

사람 입력은 스틱 크기를 그대로 속도로 쓴다(아날로그). 키보드는 이진이라
걷기 수정키를 둔다. 체력(`stamina`)이 스프린트를 실제로 제약하게 한다.
완료 판정 계측은 `movement-metrics.md`를 따른다.

### 4. 수비 재설계

**가장 큰 작업이다.** 몸집으로 막던 것을 위치와 판단으로 대체한다.

- **마킹** — 수비수가 가까운 상대 공격수를 맡아 골문 쪽 라인에 선다.
- **패스 레인 차단** — `passTarget()` 의 `laneRisk` 계산을 수비 측에서도
  써서, 수비수가 위험한 레인 위에 서게 한다.
- **슛 블록** — 슈터와 골문 사이에 몸을 넣는다. 선수가 작아진 만큼
  의도적으로 서야 막힌다.
- **태클 거리** — 현재 92단위(4.6m)는 새 크기에서 너무 멀다. 재조정.

이 단계 없이는 득점이 90분 37골에서 내려오지 않는다.

### 5. 재밸런싱

앞 네 단계가 모든 수치를 무효화한다. 마지막에 한 번에 맞춘다.

목표는 아래 「확정된 결정」에 있다 — 10분 2~3골, 승률 80/53/23%.

## 확정된 결정 (2026-08-02)

### 경기 길이와 득점 목표 — A안 `확정`

**기본 10분, 목표 총 득점 2~3골.** 선택지는 3/6/10분에서
**6 / 10 / 20분**으로 옮긴다.

실제 프로는 분당 0.03골이라 3분이면 0.09골이다. 프로토타입에서 현실
10분이 4.5골이었고 4단계(수비)를 넣으면 내려오므로, 10분 2~3골이
도달 가능하면서 축구다운 페이스다.

**저장값 마이그레이션** — 기존 `matchSec` 은 유효한 값이면 그대로 두고
없어진 값만 옮긴다. 최소 변경이 최소 놀람이다.

| 기존 | 이후 |
|---|---|
| 180 (3분) | **360** (6분) |
| 360 (6분) | 360 유지 |
| 600 (10분) | 600 유지 |
| 그 외·없음 | **600** (새 기본값) |

### 아케이드 모드는 남기지 않는다 `확정`

현재 밸런스(80/53/23%, 4.99골)는 200경기로 튜닝된 자산이지만 전환이
이걸 버린다. 두 축척을 모드로 함께 두면 밸런스 측정 대상이 두 배가 된다.
전환 직전 수치는 `balance-history.md` 에 기록으로 남긴다.

### 난이도 축은 현행 유지 `확정`

`LEVELS` 는 `react` / `aimErr` / `gk` 세 축이다. 슛·패스 시도율은 공용
`AI_ACTION_RATE = 0.88` 이며 난이도별로 나누지 않는다.
**전환에서 이 구조를 바꾸지 않는다.**

`HUMAN_ASSIST = [0.35, 0.35, 0]` 는 **유지하되 값만 재튜닝할 수 있다.**
제거하지 않는다. 단 난이도에 대해 **비증가**여야 한다(쉬움 ≥ 보통 ≥
어려움). 커밋 `a33b1df` 에서 단조 축으로 정리한 결과를 되돌리지 않는다.

### 슛 성공률의 정의 `확정`

4단계 완료 판정에 쓰므로 정의를 고정한다.

```
슛 성공률 = 슛에서 비롯된 득점 / 슛 시도
```

**현재는 측정할 수 없다.** 슛 집계가 3곳(세트피스·`kickOwned`·`collide`)
뿐이라 드리블 골인·굴절·자책·패스 득점이 슛에 안 잡힌다. 그래서
프로토타입에서 10분 득점 4.5 > 슛 4.2 가 나왔다.

4단계에서 먼저 집계를 고친다.

- 모든 득점을 `슛 득점` 또는 `비슛 득점` 중 하나로 분류한다.
- `득점 = 슛 득점 + 비슛 득점` 항등식이 성립함을 셀프테스트로 검증한다.
- 그 뒤에 슛 성공률을 측정한다.

## 검증 기준

- 평균 이동 7~9km/h, 걷는 시간 60~70%, 최고 34km/h 이하
- 슛 성공률 10~15% (현재 프로토타입 78%)
- 경기당 득점이 정한 목표 범위 안, 난이도 승률 목표 유지
- 데스크톱·모바일 세로에서 선수·공이 읽히고 미니맵으로 상황 파악 가능
- 창 크기를 바꿔도 가시 범위가 논리 단위로 동일
