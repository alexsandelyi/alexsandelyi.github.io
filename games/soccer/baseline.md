설계 제안이 아니라 현재 코드가 실제로 하는 일이다.

## 확장이 얹히는 지점

설계가 여기에 붙는다. 각 항목이 어느 문서로 이어지는지 표시했다.

### 터치라인이 벽이다

`updateBall()` 이 네 변 모두에서 공을 반발계수 `0.7` 로 튕긴다.
골문 폭(`GOAL_H = 300`) 안으로 들어올 때만 득점 판정.
**아웃 개념 자체가 없다.** → `match-rules.md`

### 공 소유 상태가 없다

`collide()` 는 닿는 순간 무조건 공을 차낸다.
`TOUCH_V = 430` 이 선수 최고속도 `P_MAX = 470` 보다 살짝 느려서, 밀어놓고
따라잡는 것이 사실상 드리블로 동작한다. 영리하지만 공을 **잡고 있는 상태가
없어서** 패스·슛 타이밍을 플레이어가 정할 수 없다. → `input-system.md`

### 슛이 조준되지 않는다

`aimAt()` 이 상대 골문 중앙 ±30% 를 랜덤으로 고른다.
스틱을 어디로 밀든 슛 방향은 같다. 조작감의 가장 큰 구멍이다.
→ `input-system.md`

### `ball.owner` 는 선언만 되고 쓰이지 않는다

`const ball = { x, y, vx, vy, owner:null }` — `owner` 를 읽거나 쓰는 코드가
없다. 소유 상태를 넣을 때 이 필드를 살린다. → `input-system.md`

### 선수 전환은 자동뿐이다

`pickControlled()` 가 공 최근접 선수를 히스테리시스 `90` 으로 고른다.
원하는 선수를 잡을 방법이 없다. → `input-system.md`

### 팀 0 은 항상 x=0 골문을 지킨다

`homePos`, `aimAt`, `gkTarget`, `passTarget`, 색상 배정이 전부
`side === 0` 을 **방향**으로 쓴다. 코트 체인지를 넣으려면 이 가정을
걷어내야 한다. → `match-rules.md`

## 난이도 파라미터

```
              speed  react  aimErr  shoot   gk
쉬움           0.86   0.50    200    0.88   0.55
보통           0.88   0.28    100    0.88   0.85
어려움         0.92   0.12     40    0.88   1.00
```

`speed` 는 좁은 범위(0.86~0.92)다. 과거 작은 표본에서 보인 계단은
2026-07-31 각 값 200경기 스윕에서 재현되지 않았다 (`balance.md`).
난이도 차이는 `speed`, `react`(반응 지연), `aimErr`(조준 오차),
`gk`(골키퍼 반응)를 포함한 전체 조합의 결과다.

우리 팀 AI 동료는 난이도와 무관하게 항상 `LEVELS[1]`(보통) + 속도 `0.92`.

## 상태 기계

```
title ──→ play ──→ goal ──→ play      (시간 남음)
            │        └────→ end       (시간 종료)
            └────────────→ end
end ──→ play (다시 하기) | title (처음으로)
```

`state` 는 이 4개뿐이다. 세트피스를 넣으면 여기에 상태가 추가된다.
→ `match-rules.md`
