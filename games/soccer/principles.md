# 설계 원칙

**상태: 확정.** 현재 구현이 이미 이 원칙 위에 서 있다. 확장 중에도 지킨다.
다른 설계 문서의 제안이 이 원칙과 충돌하면 원칙이 이긴다.

## 1. 의존성 없음

외부 라이브러리·빌드 도구를 쓰지 않는다.

런처 번들(`/index.html`)이 외부 도구로 통째로 재생성된다 — 2026-07-30
하루에만 두 번 바뀌었다. 게임을 번들 안에 넣으면 다음 재생성 때 사라진다.
그래서 게임은 번들 밖 독립 파일이어야 하고, 빌드 산출물이 아니라 브라우저가
직접 여는 파일이어야 한다.

## 2. 논리 좌표 고정

물리·AI·경기 판정은 항상 `2100 × 1360` 논리 좌표에서 계산한다
(실제 105m × 68m 를 1m = 20단위로 옮긴 것).

화면 크기와 회전은 **그리기와 입력 변환 단계에서만** 반영한다.
창 크기나 화면 방향이 경기 결과를 바꾸면 안 된다.

세로 화면에서 경기장을 90° 돌릴 때는 그리기만 돌리면 안 되고 입력 벡터도
같은 각도로 돌린다. 회전 변환의 `translate` 는 회전 *전* 좌표계에
적용되므로 필드 순서 `(x, y)` 를 그대로 쓴다.

## 3. 밸런스는 측정한다

짐작으로 숫자를 바꾸지 않는다.

`readHuman` 만 봇으로 갈아끼우고 실제 `step(1/60)` 을 반복 호출해
난이도별 최소 30경기를 돌린다. 브라우저 `requestAnimationFrame` 에
의존하지 않는다 — 백그라운드 창에서 초당 1회로 스로틀된다.

현재 목표: 승률 쉬움 73% / 보통 53% / 어려움 23%, 경기당 총 5~6골.

이 원칙이 필요한 이유는 실측된 바 있다. `speed` 파라미터는 계단 함수처럼
작동해서 — AI 가 공 경합을 이기는 임계점이 `0.87` 근처에 있다 —
`0.86 → 0.88` 만 바꿔도 승률이 67% → 27% 로 튀었다. 눈으로 읽어서는
예측할 수 없는 종류의 변화다.

## 4. 아케이드 우선

시뮬레이션 게임이 아니다. 3분 안에 재미있어야 한다.

규칙을 더할 때마다 먼저 묻는다 — **이게 플레이어를 기다리게 만드는가.**

기다리게 만든다면 둘 중 하나를 한다.

- 짧게 만든다 (세트피스 대기 시간, 자동 진행)
- 끈다 (난이도 연동, 설정에서 선택)

현실성을 위해 재미를 깎지 않는다. 실제 축구에 있다는 것은 기능을 넣는
근거가 되지 못한다.
