# 동네 축구 — 설계

`games/soccer/index.html` 의 확장 설계. 현재 구현(892줄)을 기준선으로 삼고,
무엇을 왜 바꾸는지와 그때 깨지는 것이 무엇인지를 적는다.

## 원칙

이 네 가지는 확장 중에도 지킨다. 현재 구현이 이미 이 원칙 위에 서 있다.

1. **의존성 없음.** 외부 라이브러리·빌드 도구를 쓰지 않는다. 런처 번들
   (`index.html`)이 외부 도구로 재생성되므로, 게임은 번들 밖 독립 파일로
   유지되어야 살아남는다.
2. **논리 좌표 고정.** 물리·AI 는 항상 2100×1360(1m = 20단위)에서 계산한다.
   화면 크기·회전은 그리기와 입력 변환에서만 반영한다. 창 크기가 경기
   결과를 바꾸면 안 된다.
3. **밸런스는 측정한다.** 짐작으로 숫자를 바꾸지 않는다. `readHuman` 을
   봇으로 갈아끼우고 실제 `step()` 을 돌려 난이도별 30경기씩 승률을 낸다.
4. **아케이드 우선.** 시뮬레이션이 아니라 3분 안에 재미있어야 한다. 규칙을
   더할 때마다 "이게 플레이어를 기다리게 만드는가"를 먼저 묻는다.

## 현재 상태 (기준선)

| 영역 | 구현됨 | 없음 |
|---|---|---|
| 경기장 | 105m×68m 실측, 페널티/골 에어리어, 센터서클 | 코너 아크 (그리기만 누락) |
| 인원 | 11v11, 4-4-2 고정, 양 팀 동일 | 포메이션 선택, 개인 능력치 |
| 경기 | 180초 단판, 골 후 킥오프 | 전·후반, 하프타임, 추가시간, 코트 체인지 |
| 규칙 | 골 판정만 | 아웃오브플레이 전부, 오프사이드, 파울, 카드, 교체 |
| 조작 | 이동 + 슛 + 패스 | 드리블(트래핑), 태클, 스프린트, 조준, 수동 선수 전환 |
| AI | 최근접 추격 + 포메이션 슬롯, 5개 파라미터 | 전술 개념, 오프더볼 침투, 수비 라인 |
| 모드 | 1P(3난이도) / 2P 로컬 | 토너먼트, 리그, 시즌, 승부차기 |
| 저장 | 난이도별 전적(승/무/패, 최다 득점차) | 진행 상황 저장 |

기준선에서 짚어둘 사실 몇 가지 — 설계가 여기에 얹힌다.

- **터치라인이 벽이다.** `updateBall()` 이 네 변에서 공을 0.7 반발로
  튕긴다. 골문 폭(`GOAL_H = 300`) 안으로 들어올 때만 득점. 아웃 개념 자체가
  없다.
- **공 소유 상태가 없다.** `collide()` 는 닿는 순간 무조건 공을 차낸다.
  `TOUCH_V = 430` 이 선수 최고속도 `P_MAX = 470` 보다 살짝 느려서, 밀어놓고
  따라잡는 것이 사실상 드리블로 동작한다. 영리하지만 **공을 잡고 있는
  상태가 없어서** 패스·슛 타이밍을 플레이어가 정할 수 없다.
- **슛이 조준되지 않는다.** `aimAt()` 이 상대 골문 중앙 ±30% 를 랜덤으로
  고른다. 스틱을 어디로 밀든 슛 방향은 같다. 조작감의 가장 큰 구멍이다.
- **`ball.owner` 는 선언만 되고 쓰이지 않는다.** 소유 상태를 넣을 때 이
  필드를 살린다.
- **선수 전환은 자동뿐이다.** `pickControlled()` 가 최근접 선수를
  히스테리시스 90 으로 고른다. 원하는 선수를 잡을 방법이 없다.
- **팀 0 은 항상 x=0 골문을 지킨다.** 코트 체인지를 넣으려면 이 가정을
  걷어내야 한다 (`homePos`, `aimAt`, `gkTarget`, `passTarget`, 색상 배정이
  전부 `side === 0` 을 방향으로 쓴다).

## A. 조작·플레이 감

가장 먼저 한다. 규칙을 아무리 정교하게 만들어도 공을 다루는 느낌이 없으면
의미가 없고, 태클은 파울의 전제조건이라 순서상으로도 앞에 와야 한다.

### A-1. 공 소유 상태

`ball.owner` 를 살린다. 선수 반경 안에 공이 들어오고 상대적 속도가 낮으면
**트래핑** — 공이 선수 앞 일정 거리에 붙어 함께 움직인다.

- 소유 중에는 선수 최고속도가 감소한다 (제안: `×0.88`). 이게 드리블의
  비용이고, 공 없는 수비수가 따라잡을 수 있는 근거가 된다.
- 소유는 `kickCd` 와 별개의 쿨다운을 갖는다. 차고 나서 곧바로 자기가 다시
  잡으면 패스가 무의미해진다.
- 상대가 태클하거나, 강한 접촉이 있거나, 플레이어가 차면 소유가 풀린다.

**깨지는 것:** `collide()` 전면 재작성. 현재의 "닿으면 무조건 찬다" 가
"소유 중이면 붙이고, 아니면 경합" 으로 바뀐다. 승률이 크게 흔들리므로
A 단계 끝에서 재측정이 필수다.

### A-2. 조준

슛·패스 방향을 **스틱/키 입력 방향**으로 정한다. 입력이 없으면 현재처럼
골문 자동 조준으로 폴백한다 (모바일에서 이동과 조준을 동시에 하기 어렵다).

- 조준에는 정확도 오차를 넣는다. 능력치(C-1)와 연결되고, 먼 거리 슛이
  자동으로 어려워진다.
- `aimAt()` 은 AI 전용으로 남는다.

### A-3. 액션 확장

현재 2개(슛/패스) → 4개. 버튼이 늘어나므로 모바일 레이아웃을 함께 본다.

| 액션 | 입력(키보드) | 내용 |
|---|---|---|
| 슛 | Space | 길게 누르면 파워 충전. 짧게 = 낮고 빠른 슛 |
| 짧은 패스 | Shift | 가장 좋은 동료에게. 현재 `passTarget()` 개선 |
| 스루패스 | Ctrl(가칭) | 동료의 **진행 방향 앞 공간**으로. 침투와 짝 |
| 태클 | Space(수비 시) | 공 없는 상태에서 슛 버튼 = 태클. 버튼 재사용 |

**모바일:** 버튼 4개는 엄지에 과하다. 공 소유 여부로 버튼 2개의 의미를
바꾼다 — 소유 중이면 [슛][패스], 아니면 [태클][선수전환]. 화면에 라벨을
바꿔 표시한다.

### A-4. 수동 선수 전환

전환 버튼을 추가한다. 누를 때마다 공 기준 가까운 순서로 순환.
자동 전환은 유지하되, 수동으로 잡은 직후 짧은 시간(≈1.2초)은 자동 전환을
막는다. 그러지 않으면 눌러도 곧바로 되돌아간다.

### A-5. 스프린트와 체력

스프린트(속도 `×1.25`)를 넣고 체력 게이지로 제한한다. 무제한이면 항상
누르고 있게 되어 없는 것과 같다.

체력은 능력치(C-1)와 경기 후반 페이스 저하에 함께 쓰인다. 다만 **3분
경기에서 체력이 유의미하게 닳는가**가 미결이다 — 전·후반제(B-4)로 경기
시간이 늘어난 뒤에 도입 여부를 재검토한다.

### A-6. 열린 질문

- 파워 충전 슛은 모바일에서 "누르고 있는 동안 이동 불가" 문제가 있다.
  탭=일반 슛 / 롱프레스=강슛 으로 충분한가?
- 트래핑 거리를 고정으로 둘 것인가, 진행 속도에 비례시킬 것인가.

## B. 경기 규칙·심판

새 상태 기계가 필요한 단계다. 현재 `state` 는
`title | play | goal | end` 뿐이다. 여기에 `setpiece` 를 더한다.

### B-1. 아웃오브플레이

터치라인의 벽 반사를 제거하고, 공이 선을 넘으면 마지막 터치한 팀을 근거로
재개 방식을 정한다.

| 넘은 선 | 마지막 터치 | 재개 |
|---|---|---|
| 사이드라인 | 어느 쪽이든 | 스로인 (반대 팀) |
| 골라인, 공격 측 터치 | 공격 팀 | 골킥 |
| 골라인, 수비 측 터치 | 수비 팀 | 코너킥 |

**전제:** "마지막 터치" 추적. `collide()` 에서 `ball.lastTouch = p` 를
기록한다. 오프사이드(B-3)와 파울(B-2)도 이 값을 쓴다.

### B-2. 세트피스 상태 기계

스로인·골킥·코너킥·프리킥·킥오프를 **하나의 흐름**으로 처리한다.

```
setpiece {
  type: 'throw' | 'goalkick' | 'corner' | 'free' | 'kickoff' | 'penalty',
  side,           // 차는 팀
  spot: {x, y},   // 공 위치
  taker,          // 차는 선수
  timer           // 자동 진행까지 남은 시간
}
```

흐름: 공을 `spot` 에 고정 → 상대 선수를 `spot` 에서 9.15m 밖으로 밀어냄
→ `taker` 를 공 옆으로 이동 → 플레이어 팀이면 조준 입력 대기(최대 3초,
초과 시 자동), AI 면 짧은 지연 후 자동 → 차면 `play` 복귀.

**아케이드 원칙 적용:** 세트피스는 게임을 멈춘다. 대기 시간을 짧게
(스로인 0.8초, 코너 1.5초) 잡고, 선수 재배치는 순간이동이 아니라
빠른 보간으로 처리해 흐름이 끊긴 느낌을 줄인다.

`resetPositions()` 는 킥오프 전용에서 세트피스 배치 함수로 일반화한다.

### B-3. 오프사이드

**도입하되 난이도에 연동한다.** 아케이드 게임에서 오프사이드는 플레이어가
이유를 모른 채 공격이 무산되는 최대 원인이다.

- 판정 시점: **패스를 차는 순간**. 받는 선수가 뒤에서 두 번째 수비수보다
  앞이고 공보다 앞이면 표시해 두고, 그 선수가 공을 잡으면 프리킥.
- 시각 피드백이 필수다. 판정 시 오프사이드 라인을 잠깐 그려준다.
- 난이도별: 쉬움 = 끄기 / 보통 = 켜기 / 어려움 = 켜기.

미결: 우리 팀 AI 동료가 오프사이드를 피해 움직여야 한다. 그러지 않으면
플레이어가 통제 못 하는 이유로 계속 끊긴다. `slotTarget()` 에 수비 라인
인식을 넣는 작업이 딸려온다.

### B-4. 경기 진행

- **전·후반제.** 180초 단판 → 90초 × 2. 하프타임에 **코트 체인지**.
  위에 적었듯 `side === 0` 을 방향으로 쓰는 코드 전부가 영향을 받는다.
  깔끔한 방법은 팀별 `attackDir` 필드를 두고 모든 방향 계산을 그리로
  돌리는 것이다.
- 경기 길이는 설정에서 고를 수 있게 한다 (3분 / 6분 / 10분).
- 추가시간: 세트피스로 멈춘 시간을 누적해 후반 끝에 더한다. 구현은 쉽고
  축구다운 맛이 난다.

### B-5. 파울과 카드

태클(A-3)이 들어온 뒤에 성립한다.

- 태클이 공보다 선수를 먼저 맞히면 파울 → 프리킥. 페널티 에어리어 안이면
  PK.
- 속도·각도로 심각도를 매긴다: 경고 없음 / 옐로 / 레드(퇴장, 10명).
- 퇴장은 포메이션 재배치가 필요하다 (11명 고정 배열이 깨진다).

미결: 퇴장까지 구현하면 인원 가변 처리가 `FORMATION` 전반에 파급된다.
1차에는 **옐로카드까지만** 넣고 레드는 C 단계 이후로 미루는 것을 제안한다.

### B-6. 넣지 않을 것

명시적으로 제외한다 — 아케이드 원칙에 반한다.

- VAR, 부상, 날씨, 심판 성향
- 골키퍼 백패스 규칙, 6초 규칙
- 교체는 B 에서 제외하고 D(시즌 모드)에서 필요해지면 다룬다

## C. 팀·전술·선수 상성

여기서 "양 팀이 동일하다" 는 전제가 사라진다. **난이도 파라미터의 의미가
바뀌므로 C 단계 후 밸런스 전면 재측정이 필요하다.**

### C-1. 선수 능력치

5개로 제한한다. 많으면 튜닝이 불가능해지고 플레이어도 못 읽는다.

| 능력치 | 영향 |
|---|---|
| 속도 | `P_MAX` 배수 |
| 슛 | 슛 속도, 조준 오차 |
| 패스 | 패스 정확도, 스루패스 성공률 |
| 수비 | 태클 성공률, 소유 경합 |
| 체력 | 스프린트 지속, 후반 페이스 저하 |

골키퍼는 별도로 `선방` 하나를 더 갖는다 (`reach` 배수와 `gkTarget` 반응).

값은 1~99, 화면에는 5단계 막대로만 보여준다. 숫자를 그대로 노출하면
플레이어가 최적화 게임을 하게 되고, 이 게임의 관심사가 아니다.

### C-2. 포메이션

`FORMATION` 상수를 테이블로 바꾼다. 4-4-2 / 4-3-3 / 3-5-2 / 5-3-2.

각 포메이션은 정규화 좌표 배열 + 역할(GK/DF/MF/FW)만 갖는다. 현재 구조가
이미 정규화 좌표라 확장이 자연스럽다.

### C-3. 전술

**현재 `slotTarget()` 의 상수들이 그대로 전술 슬라이더가 된다.** 새 개념을
발명할 필요가 없다.

| 전술 | 현재 상수 | 범위 |
|---|---|---|
| 수비 라인 높이 | `DF` 클램프 `FW * 0.58` | 0.45 ~ 0.70 |
| 압박 강도 | `shiftX = 0.42` | 0.25 ~ 0.55 |
| 폭 | `shiftY = 0.30` | 0.20 ~ 0.45 |
| 추격 인원 | 최근접 1명 고정 | 1 ~ 2명 |

### C-4. 상성

전술 간 가위바위보를 만든다. 이것이 "상성" 의 실체다.

- **높은 수비 라인 ↔ 빠른 공격수:** 라인이 높으면 중원을 지배하지만
  배후 공간이 열린다. 상대에 속도 능력치가 높은 FW 가 있으면 역습에 취약.
- **강한 압박 ↔ 패스 능력:** 압박이 세면 공을 빨리 뺏지만 대형이 벌어진다.
  상대 패스 능력이 높으면 압박을 통과당한다.
- **좁은 폭 ↔ 측면 공격:** 중앙을 잠그면 코너·크로스에 약해진다.

각 상성은 **이미 있는 물리로 자연히 발생**해야 한다. 별도 보정 계수를
곱해 인위적으로 만들지 않는다. 발생하지 않으면 시뮬레이션으로 확인하고
상수 범위를 조정한다.

### C-5. 팀

동네 축구 정체성에 맞는 팀 8~12개. 팀마다 포메이션 선호, 전술 성향,
능력치 분포가 다르다. 팀 종합 등급은 선수 능력치에서 파생시킨다(직접
입력하지 않는다 — 어긋나면 디버깅이 불가능해진다).

### C-6. 열린 질문

- 난이도(`LEVELS`)와 팀 강함이 **둘 다** 있으면 중복이다. 난이도를
  없애고 팀 선택으로 대체할 것인가, 아니면 난이도는 AI 반응속도만 담당하고
  팀은 능력치만 담당하도록 축을 분리할 것인가? → **축 분리를 제안한다.**
  난이도 = 상대 AI 의 반응·판단 (`react`, `aimErr`, `gk`),
  팀 = 선수 능력치. `speed` 는 능력치로 이관.

## D. 게임 모드·진행 구조

경기가 재미있어진 뒤에 얹는다. 순서를 뒤집으면 재미없는 경기를 여러 번
하게 만드는 구조가 된다.

### D-1. 모드

| 모드 | 내용 |
|---|---|
| 빠른 경기 | 현재의 1P/2P 단판. 유지 |
| 토너먼트 | 8팀 녹아웃 3라운드. 무승부 시 승부차기 |
| 리그 | 8팀 풀리그 14경기, 승점 순위표 |
| 시즌 | 리그 + 컵. 여러 시즌 누적 |

토너먼트를 먼저 만든다. 짧고(3경기), 승부차기라는 새 재미가 붙고,
리그·시즌의 뼈대(대진·기록·저장)를 그대로 재사용할 수 있다.

### D-2. 승부차기

녹아웃의 전제. 별도의 미니 상태 기계 — 5번씩, 동률이면 서든데스.
기존 물리를 쓰되 조준(A-2)과 골키퍼 방향 선택만 있으면 된다.
분량 대비 재미가 가장 큰 항목이다.

### D-3. 저장

`localStorage` 키를 정리한다. 현재 `ilbbang.soccer11.v1.rec{n}`,
`.lvl` 두 종류가 흩어져 있다.

```
ilbbang.soccer11.v2 = {
  version: 2,
  settings: { level, matchLen, offside, team },
  records:  { [level]: {w, d, l, bestGd} },   // v1 에서 이관
  progress: { mode, round, fixtures[], table[], … } | null
}
```

단일 키 + `version` 필드로 바꾼다. 마이그레이션 함수를 두고 v1 전적을
가져온다 — 플레이어의 기록을 날리지 않는다.

### D-4. 기록

경기 후 요약: 점유율, 슈팅/유효슈팅, 코너, 파울. 대부분 이미 있는
이벤트를 세기만 하면 된다. 점유율은 `ball.owner`(A-1) 의 팀별 누적 시간.

## 구현 순서

각 단계 끝에서 **반드시 시뮬레이션 재측정**을 한다. 앞 단계가 승률을
바꿔놓기 때문이다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | A. 조작 (소유·조준·태클·전환) | 승률 재측정, 목표 73/53/23% 복원 |
| 2 | B. 규칙 (아웃·세트피스·전후반) | 경기당 5~6골 유지, 세트피스로 흐름이 끊기지 않음 |
| 3 | B. 오프사이드·파울 | 오프사이드 판정이 경기당 3회 이하 |
| 4 | C. 팀·전술 | 팀 등급차가 승률에 단조 반영, 상성이 측정에서 관찰됨 |
| 5 | D. 토너먼트 + 승부차기 | 3라운드 완주, 저장·복원 동작 |
| 6 | D. 리그·시즌·기록 | — |

**공개는 전 단계 완료 후 1회.** 중간 상태는 로컬 커밋으로만 보관한다
(`CLAUDE.md` 참조).

## 미결 — 사용자 결정 필요

1. **파일 분할.** 892줄이 3~4배가 된다. 한 파일을 유지할지, ES 모듈로
   나눌지(`engine.js` / `ai.js` / `rules.js` / `ui.js`). 모듈은 빌드 없이
   동작하지만 `file://` 직접 열기가 막히고 HTTP 서버가 필요해진다.
   → 3000줄을 넘어가는 시점에 분할을 제안한다.
2. **난이도 vs 팀 강함** 의 축 분리 (C-6).
3. **오프사이드** 도입 강도 — 난이도 연동으로 충분한가.
4. **목표 승률 73/53/23%** 를 계속 목표로 둘 것인가. 팀 선택이 생기면
   "보통 난이도 + 약팀" 같은 조합이 생겨 단일 목표가 성립하지 않는다.
5. **레드카드**(인원 가변)를 1차에 넣을 것인가.
