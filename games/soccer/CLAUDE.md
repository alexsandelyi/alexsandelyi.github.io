# 동네 축구 — 작업 지침

`games/soccer/` 와 모든 하위 경로에 적용된다. 루트 `CLAUDE.md` 의 규칙도
그대로 적용되며, 충돌하면 **더 안전하고 더 구체적인 쪽**을 따르고 사용자에게
충돌 내용을 알린다.

같은 폴더의 `AGENTS.md` 와 같은 사실을 공유한다. 한쪽을 고치면 다른 쪽도
함께 고친다.

## 공개는 완성 후 한 번에

축구 게임의 중간 상태는 원격 저장소에 올리지 않는다. 저장소가 Public 이라
작업 브랜치를 올리는 것도 소스 공개에 해당한다. 수정과 커밋은 로컬에만
보관하고, 최종 검증 후 그 1회의 push 승인을 명시적으로 받는다.

## 설계 문서

문서 목차는 `README.md` 에 있다. 새 문서를 만들면 목차에 한 줄 추가한다.

| 규칙 | 이유 |
|---|---|
| 이 폴더 **바로 아래**에 둔다. `docs/`, `design/` 같은 하위 디렉터리를 만들지 않는다 | 게임이 한 폴더로 완결되게 유지한다 |
| 파일명은 영문 소문자 kebab-case (`match-rules.md`) | — |
| **200줄 이하** | 넘으면 글자를 압축하지 말고 주제별로 파일을 나눈다 |
| 한 파일에 한 주제 | — |

줄 수 확인 — 200줄을 넘는 파일이 있으면 설계 작업을 완료로 보고하지 않는다.

```bash
wc -l games/soccer/*.md
```

### 문서에 적는 것

- 목적, 범위, 핵심 규칙, 데이터·상태의 흐름, 예외 상황, 검증 기준.
- **확정 / 제안 / 미결을 명확히 구분한다.** 문서 첫머리에 상태를 적는다.
- 코드와 일치해야 하는 수치·좌표계·상태 전이·인터페이스는 모호하지 않게.
- 구현 코드를 길게 복사하지 않는다. 짧은 의사코드와 인터페이스 예시만.
- **밸런스 수치를 추측으로 확정하지 않는다.** 시뮬레이션 조건과 측정 결과를
  함께 적는다.

### 설계와 구현의 동기화

중요한 동작이나 규칙을 구현하기 **전에** 관련 문서를 쓰거나 갱신한다.
구현이 설계와 달라졌으면 같은 작업에서 문서를 고친다 — 차이가 남은 상태로
완료를 선언하지 않는다.

문서를 고친 것만으로 구현이 검증됐다고 판단하지 않는다.

## 코드 파일 500줄

**코드 파일은 500줄을 넘지 않는다** (설계 문서는 200줄). 넘으면 글자를
압축하지 말고 책임별로 나눈다.

```bash
for f in games/soccer/js/*.js tools/*.js; do
  c=$(wc -l < "$f"); [ "$c" -gt 500 ] && echo "초과: $f ($c)"
done
```

### 게임은 클래식 `<script src>` 로 나눈다

`games/soccer/js/NN-이름.js` 를 `index.html` 이 순서대로 부른다.
**ES 모듈이 아니다.** 클래식 스크립트는 전역 스코프를 공유하므로

- 빌드도 `import`/`export` 도 필요 없다 (`principles.md` 1번)
- 측정 도구가 파일을 순서대로 vm 에 올려 브라우저와 같은 스코프를 만든다

모듈로 바꾸면 두 가지가 모두 깨진다.

### 로드 순서가 곧 의존 순서다

**호이스팅은 파일 안에서만 동작한다.** 앞 파일의 최상위 코드가 뒤 파일의
함수를 참조하면 `ReferenceError` 다. 실제로 겪었다 — `10-hud.js` 가
`11-practice.js` 의 `startPractice` 를 등록하다 터졌다. 콜백 안에서
부르거나 화살표로 감싸면 호출 시점에 찾으므로 안전하다.

```js
addEventListener('click', () => startPractice());   // 뒤 파일의 함수
```

`const` 는 앞 파일 것을 뒤 파일에서 참조할 수만 있다. 반대는 TDZ 다.

**측정 도구는 파일을 한 장씩 실행해 이 규칙을 검사한다.** 이어 붙이면
호이스팅이 전체에 걸쳐 되살아나 이 버그를 놓친다.

### 캐시 무효화 `?v=`

`index.html` 이 `js/NN-x.js?v=해시` 로 부른다. 해시는 `js/` 전체 내용에서
나오므로 **파일을 고치면 스탬프도 갱신해야 한다.**

```bash
node tools/soccer-sim.js --restamp
```

안 갱신하면 브라우저가 옛 파일을 계속 쓴다. 배포 뒤에는 더 나쁘다 —
바뀐 파일만 새로 받고 나머지는 캐시라 **옛 JS 와 새 JS 가 섞인다.**

셀프테스트의 `versionStampFresh` 가 이걸 잡는다.

**검증할 때는 HTML 에도 쿼리를 붙인다.** `?v=` 는 JS 만 무효화하므로,
HTML 자체가 캐시돼 있으면 옛 `?v=` 를 계속 본다. 실제로 이것 때문에
고친 코드가 안 도는 줄 알고 두 번 헤맸다.

### 파일마다 `'use strict'`

독립 스크립트라 지시어도 파일마다 필요하다. 주석·빈 줄은 지시어
프롤로그를 깨지 않으므로 헤더 주석 뒤에 와도 된다.
셀프테스트의 `everyFileStrict` 가 검사한다.

## 좌표계

물리·AI·경기 판정은 항상 `2100 × 1360` 논리 좌표에서 계산한다
(실제 105m × 68m 를 1m = 20단위로). 화면 크기와 회전은 그리기와 입력 변환
단계에서만 반영한다. 창 크기가 경기 결과를 바꾸면 안 된다.

세로 화면에서는 경기장을 90° 돌린다. **그리기만 돌리면 안 되고 입력 벡터도
같은 각도로 돌린다.** 회전 변환의 `translate` 는 회전 *전* 좌표계에
적용되므로 필드 순서 `(x, y)` 를 그대로 쓴다 (뒤집어 써서 경기장이 화면 폭의
63% 만 채우는 버그가 있었다).

## 수치 측정은 사용자가 직접 한다 (2026-08-05)

사용자 지시다 — "앞으로 측정하지마 사용자가 직접 측정할꺼야".
그 자리에서 범위를 확인했다: **수치 측정만 금지.**

**하지 않는 것** — `soccer-sim.js -n ...` 경기 배치, `soccer-lab.js`,
브라우저에서 속도·정점·거리 같은 실측 표를 뽑는 것. 요청받았을 때만
실행하고, 먼저 돌리거나 "측정해서 확인하겠다"고 제안하지 않는다.

**계속하는 것** — 아래 둘은 수치를 뽑는 게 아니라 깨진 것을 잡는 장치다.

```bash
node tools/soccer-sim.js --restamp     # js/ 를 고치면 필수
node tools/soccer-sim.js --self-test   # 통과/실패 검사
```

측정하지 않은 값은 **모른다고 적는다.** 짐작해서 "이 정도일 것"이라고
단정하지 않는다. 확인이 필요해 보이면 실행하지 말고 명령어와 볼 지점을
알려주고 넘긴다.

**승률·득점 목표에 맞춘 상수 튜닝(재밸런싱)도 하지 않는다** — 별도의
사용자 지시다. `principles.md` 의 목표값은 참고값이지 강제값이 아니다.

### 도구와 기준선은 유지한다

사용자가 돌릴 때를 위한 사실만 남긴다.

- `soccer-sim.js` 는 `readHuman` 만 봇으로 갈아끼우고 실제 `step(1/60)` 을
  반복 호출한다. 브라우저 `requestAnimationFrame` 에 의존하지 않는다 —
  백그라운드 창에서 초당 1회로 스로틀된다.
- **판정에는 난이도별 200경기 이상**이 필요하다. 30경기의 승률은 95%
  신뢰구간이 ±18%p 라 난이도 간 차이가 묻힌다.
- 과거 30경기에서 `speed` 가 `0.87` 근처의 계단처럼 보였지만, 각 값
  200경기 스윕에서는 가장 큰 인접 변화가 8.5%p 였고 모든 인접 신뢰구간이
  겹쳤다. 작은 표본의 급변을 임계점으로 확정하지 않는다.

## 검증

코드만 읽고 "될 것" 이라고 판단하지 않는다. 로컬 서버로 실제로 연다.

```bash
python -m http.server 8899   # 끝나면 프로세스를 정리한다
```

데스크톱·태블릿·모바일 크기와 세로 화면을 함께 본다.

여기서 보는 것은 **도는지 / 보이는지**다. 수치를 뽑아 표로 만드는 것은
위의 「수치 측정은 사용자가 직접 한다」에 걸린다.

구현을 손으로 확인하는 방법 — 연습 모드, 키 배치, 기능 실측 도구는
[practice-mode.md](practice-mode.md) 에 있다.
