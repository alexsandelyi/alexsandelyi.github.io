# 동네 축구 — 작업 지침

`games/soccer/` 와 모든 하위 경로에 적용된다. 루트 `CLAUDE.md` 의 규칙도
그대로 적용되며, 충돌하면 **더 안전하고 더 구체적인 쪽**을 따르고 사용자에게
충돌 내용을 알린다.

같은 폴더의 `AGENTS.md` 와 같은 사실을 공유한다. 한쪽을 고치면 다른 쪽도
함께 고친다.

## 공개는 완성 후 한 번에

축구 게임의 중간 상태는 원격 저장소에 올리지 않는다. 저장소가 Public 이라
작업 브랜치를 올리는 것도 소스 공개에 해당한다. 수정과 커밋은 로컬에만
보관하고, 최종 검증 후 그 1회의 push 승인을 명시적으로 받는다.

## 설계 문서를 두지 않는다 (2026-08-13)

`games/soccer/*.md` 설계 문서 24개를 지웠다. 코드가 3062줄이라 직접 읽을 수
있고, 낡은 문서가 현재 사실인 척하는 쪽이 더 위험했기 때문이다 — 실제로
루트 `README.md` 는 없어진 지 오래인 "한 파일" 구성과 1440px 상한을 계속
설명하고 있었다.

- **새 `.md` 를 만들지 않는다.** 알아야 할 사실은 이 파일이나 코드 주석에
  적는다. 이 파일이 길어지면 그때 나눈다.
- 지운 문서는 git 에 남아 있다. 필요하면 꺼내 보되 **현재 사실로 믿지
  않는다** — 지운 시점에 이미 코드와 어긋난 것이 있었다.

```bash
git show 267d550:games/soccer/balance.md   # 지우기 직전 커밋
```

아래 두 절은 **코드에서 복원할 수 없어서** 문서에서 옮겨온 것이다.

## 밸런스 기준선 (2026-08-02 측정, `balance.md` 에서 옮김)

내가 시뮬레이션을 돌리지 않으므로(아래 「수치 측정은 사용자가 직접 한다」)
이 표가 유일한 출처다. **코드를 고쳐도 자동으로 갱신되지 않는다** — 사용자가
다시 측정해 알려줄 때만 바꾼다. 조건이 다르면 비교할 수 없다.

```
명령      node tools/soccer-sim.js -n 200 --seed 1
경기 수   난이도당 200
시드      1 (mulberry32)
봇        사람 자리에 aiPlayer + LEVELS[1](보통), isChaser=true
경기 길이 600초
```

현실 계측치 전환 5단계 최종. `LEVELS gk=0.85/1.15/1.55`,
`HUMAN_ASSIST=1.00/0.35/0`.

| 난이도 | 승/무/패 | 승률 (95% CI) | 총득점 | 슛/경기 | 성공률 |
|---|---:|---:|---:|---:|---:|
| 쉬움 | 159/38/3 | 79.5% (73.4~84.5) | 2.58 | 22.23 | 11.5% |
| 보통 | 105/45/50 | 52.5% (45.6~59.3) | 2.60 | 25.34 | 10.1% |
| 어려움 | 44/44/112 | 22.0% (16.8~28.2) | 2.82 | 28.02 | 10.0% |

통합 총득점 2.67. 참고 목표(강제값이 아니다)는 승률 80/53/23%, 난이도별
총득점 2~3, 슛 성공률 10~15% 였고 위 표는 셋 다 만족한 상태다.

## 스프라이트 — 실패한 방법 (`sprite-sources.md` 에서 옮김)

코드에는 성공한 것만 남는다. 같은 걸 다시 시도하지 않기 위한 기록이다.

- **컷아웃 퍼펫은 실패했다** (2026-08-12). 서 있는 일러스트를 부위로 잘라
  관절에서 돌려 킥 포즈를 만들려 했다. 분리도 회전도 됐지만 결과가 `idle`
  과 구분되지 않았다. 원본이 뒤에서 본 각도라 다리를 2D 로 돌려도 몸
  실루엣 안에서만 움직인다 — 실제 킥은 원근이 바뀌는 동작이다. `gk-dive`
  만 몸 전체를 65~85° 돌려 쓸 만했다. 되돌렸다.
- **생성 포즈는 단축 정도가 다르다** (2026-08-13). 남은 10포즈를
  `sprite-ai` 로 뽑아 넣었더니 몸길이가 손 일러스트 58(`idle`·`walk`)·
  51(`run`) 대 생성본 20~31 이었다. **배율 버그가 아니다** — 손 일러스트는
  몸이 길게 뻗어 있고 생성본은 정사각형으로 눌려 있다. 어깨 폭(`KIT_W`)을
  맞추면 길이가 절반이 되고, 길이를 맞추면 어깨가 두 배가 된다. 배율로는
  못 고친다. 같은 단축으로 그린 새 원본이 필요하다.
- 프롬프트에 `camera_perspective: top_down` 만 넣으면 눈높이 뒷모습이
  나온다. "카메라가 바로 위에서 내려다본다 / 정수리와 어깨가 먼저 보인다"를
  문장으로 박아야 톱다운 각도가 나온다.
- 배경 제거는 **테두리에서 흰색을 타고 들어가는 flood fill** 이다. 밝은
  픽셀을 전부 지우면 흰 축구화에 구멍이 난다.
- **크기 기준은 어깨 폭이다.** 전체 길이로 맞추면 달릴 때 뒤로 뻗은 다리
  때문에 선수가 작아지고 서 있을 때 커진다.

## 코드 파일 500줄

**코드 파일은 500줄을 넘지 않는다.** 넘으면 글자를 압축하지 말고 책임별로
나눈다.

```bash
for f in games/soccer/js/*.js tools/*.js tools/*.py; do
  c=$(wc -l < "$f"); [ "$c" -gt 500 ] && echo "초과: $f ($c)"
done
```

### 게임은 클래식 `<script src>` 로 나눈다

`games/soccer/js/NN-이름.js` 를 `index.html` 이 순서대로 부른다.
**ES 모듈이 아니다.** 클래식 스크립트는 전역 스코프를 공유하므로

- 빌드도 `import`/`export` 도 필요 없다 (의존성 없음이 이 게임의 원칙이다)
- 측정 도구가 파일을 순서대로 vm 에 올려 브라우저와 같은 스코프를 만든다

모듈로 바꾸면 두 가지가 모두 깨진다.

### 로드 순서가 곧 의존 순서다

**호이스팅은 파일 안에서만 동작한다.** 앞 파일의 최상위 코드가 뒤 파일의
함수를 참조하면 `ReferenceError` 다. 실제로 겪었다 — `11-hud.js` 가
`12-practice.js` 의 `startPractice` 를 등록하다 터졌다. 콜백 안에서
부르거나 화살표로 감싸면 호출 시점에 찾으므로 안전하다.

```js
addEventListener('click', () => startPractice());   // 뒤 파일의 함수
```

`const` 는 앞 파일 것을 뒤 파일에서 참조할 수만 있다. 반대는 TDZ 다.

**측정 도구는 파일을 한 장씩 실행해 이 규칙을 검사한다.** 이어 붙이면
호이스팅이 전체에 걸쳐 되살아나 이 버그를 놓친다.

### 캐시 무효화 `?v=`

`index.html` 이 `js/NN-x.js?v=해시` 로 부른다. 해시는 `js/` 전체 내용에서
나오므로 **파일을 고치면 스탬프도 갱신해야 한다.**

```bash
node tools/soccer-sim.js --restamp
```

안 갱신하면 브라우저가 옛 파일을 계속 쓴다. 배포 뒤에는 더 나쁘다 —
바뀐 파일만 새로 받고 나머지는 캐시라 **옛 JS 와 새 JS 가 섞인다.**

스프라이트 시트도 같은 문제가 있다. `sprite-gen.py` 가 `09-sprites.js` 의
`SPRITE_V` 를 갱신하므로 **두 명령을 이어서** 돌린다.

```bash
python tools/sprite-gen.py            # 시트 + SPRITE_V
node tools/soccer-sim.js --restamp    # index.html 의 ?v=
```

셀프테스트의 `versionStampFresh` 가 이걸 잡는다.

**검증할 때는 HTML 에도 쿼리를 붙인다.** `?v=` 는 JS 만 무효화하므로,
HTML 자체가 캐시돼 있으면 옛 `?v=` 를 계속 본다. 실제로 이것 때문에
고친 코드가 안 도는 줄 알고 두 번 헤맸다.

### 파일마다 `'use strict'`

독립 스크립트라 지시어도 파일마다 필요하다. 주석·빈 줄은 지시어
프롤로그를 깨지 않으므로 헤더 주석 뒤에 와도 된다.
셀프테스트의 `everyFileStrict` 가 검사한다.

## 좌표계

물리·AI·경기 판정은 항상 `2100 × 1360` 논리 좌표에서 계산한다
(실제 105m × 68m 를 1m = 20단위로). 화면 크기와 회전은 그리기와 입력 변환
단계에서만 반영한다. 창 크기가 경기 결과를 바꾸면 안 된다.

세로 화면에서는 경기장을 90° 돌린다. **그리기만 돌리면 안 되고 입력 벡터도
같은 각도로 돌린다.** 회전 변환의 `translate` 는 회전 *전* 좌표계에
적용되므로 필드 순서 `(x, y)` 를 그대로 쓴다 (뒤집어 써서 경기장이 화면 폭의
63% 만 채우는 버그가 있었다).

## 수치 측정은 사용자가 직접 한다 (2026-08-05)

사용자 지시다 — "앞으로 측정하지마 사용자가 직접 측정할꺼야".
그 자리에서 범위를 확인했다: **수치 측정만 금지.**

**하지 않는 것** — `soccer-sim.js -n ...` 경기 배치, `soccer-lab.js`,
브라우저에서 속도·정점·거리 같은 실측 표를 뽑는 것. 요청받았을 때만
실행하고, 먼저 돌리거나 "측정해서 확인하겠다"고 제안하지 않는다.

**계속하는 것** — 아래 둘은 수치를 뽑는 게 아니라 깨진 것을 잡는 장치다.

```bash
node tools/soccer-sim.js --restamp     # js/ 를 고치면 필수
node tools/soccer-sim.js --self-test   # 통과/실패 검사
```

측정하지 않은 값은 **모른다고 적는다.** 짐작해서 "이 정도일 것"이라고
단정하지 않는다. 확인이 필요해 보이면 실행하지 말고 명령어와 볼 지점을
알려주고 넘긴다.

**승률·득점 목표에 맞춘 상수 튜닝(재밸런싱)도 하지 않는다** — 별도의
사용자 지시다. 위 「밸런스 기준선」의 목표값은 참고값이지 강제값이 아니다.

### 도구와 기준선은 유지한다

사용자가 돌릴 때를 위한 사실만 남긴다.

- `soccer-sim.js` 는 `readHuman` 만 봇으로 갈아끼우고 실제 `step(1/60)` 을
  반복 호출한다. 브라우저 `requestAnimationFrame` 에 의존하지 않는다 —
  백그라운드 창에서 초당 1회로 스로틀된다.
- **판정에는 난이도별 200경기 이상**이 필요하다. 30경기의 승률은 95%
  신뢰구간이 ±18%p 라 난이도 간 차이가 묻힌다.
- 과거 30경기에서 `speed` 가 `0.87` 근처의 계단처럼 보였지만, 각 값
  200경기 스윕에서는 가장 큰 인접 변화가 8.5%p 였고 모든 인접 신뢰구간이
  겹쳤다. 작은 표본의 급변을 임계점으로 확정하지 않는다.

## 검증

코드만 읽고 "될 것" 이라고 판단하지 않는다. 로컬 서버로 실제로 연다.

```bash
python -m http.server 8899   # 끝나면 프로세스를 정리한다
```

데스크톱·태블릿·모바일 크기와 세로 화면을 함께 본다.

여기서 보는 것은 **도는지 / 보이는지**다. 수치를 뽑아 표로 만드는 것은
위의 「수치 측정은 사용자가 직접 한다」에 걸린다.

연습 모드·키 배치·실측 도구는 코드에 있다 — `js/12-practice.js` 가 본체,
진입 버튼과 키 안내는 `js/11-hud.js` 다.
