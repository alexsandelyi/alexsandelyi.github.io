# 동네 축구 — 작업 지침

`games/soccer/` 와 모든 하위 경로에 적용된다. 루트 `CLAUDE.md` 의 규칙도
그대로 적용되며, 충돌하면 **더 안전하고 더 구체적인 쪽**을 따르고 사용자에게
충돌 내용을 알린다.

같은 폴더의 `AGENTS.md` 와 같은 사실을 공유한다. 한쪽을 고치면 다른 쪽도
함께 고친다.

## 공개는 완성 후 한 번에

축구 게임의 중간 상태는 원격 저장소에 올리지 않는다. 저장소가 Public 이라
작업 브랜치를 올리는 것도 소스 공개에 해당한다. 수정과 커밋은 로컬에만
보관하고, 최종 검증 후 그 1회의 push 승인을 명시적으로 받는다.

## 설계 문서

문서 목차는 `README.md` 에 있다. 새 문서를 만들면 목차에 한 줄 추가한다.

| 규칙 | 이유 |
|---|---|
| 이 폴더 **바로 아래**에 둔다. `docs/`, `design/` 같은 하위 디렉터리를 만들지 않는다 | 게임이 한 폴더로 완결되게 유지한다 |
| 파일명은 영문 소문자 kebab-case (`match-rules.md`) | — |
| **200줄 이하** | 넘으면 글자를 압축하지 말고 주제별로 파일을 나눈다 |
| 한 파일에 한 주제 | — |

줄 수 확인 — 200줄을 넘는 파일이 있으면 설계 작업을 완료로 보고하지 않는다.

```bash
wc -l games/soccer/*.md
```

### 문서에 적는 것

- 목적, 범위, 핵심 규칙, 데이터·상태의 흐름, 예외 상황, 검증 기준.
- **확정 / 제안 / 미결을 명확히 구분한다.** 문서 첫머리에 상태를 적는다.
- 코드와 일치해야 하는 수치·좌표계·상태 전이·인터페이스는 모호하지 않게.
- 구현 코드를 길게 복사하지 않는다. 짧은 의사코드와 인터페이스 예시만.
- **밸런스 수치를 추측으로 확정하지 않는다.** 시뮬레이션 조건과 측정 결과를
  함께 적는다.

### 설계와 구현의 동기화

중요한 동작이나 규칙을 구현하기 **전에** 관련 문서를 쓰거나 갱신한다.
구현이 설계와 달라졌으면 같은 작업에서 문서를 고친다 — 차이가 남은 상태로
완료를 선언하지 않는다.

문서를 고친 것만으로 구현이 검증됐다고 판단하지 않는다.

## 좌표계

물리·AI·경기 판정은 항상 `2100 × 1360` 논리 좌표에서 계산한다
(실제 105m × 68m 를 1m = 20단위로). 화면 크기와 회전은 그리기와 입력 변환
단계에서만 반영한다. 창 크기가 경기 결과를 바꾸면 안 된다.

세로 화면에서는 경기장을 90° 돌린다. **그리기만 돌리면 안 되고 입력 벡터도
같은 각도로 돌린다.** 회전 변환의 `translate` 는 회전 *전* 좌표계에
적용되므로 필드 순서 `(x, y)` 를 그대로 쓴다 (뒤집어 써서 경기장이 화면 폭의
63% 만 채우는 버그가 있었다).

## 밸런스는 측정한다

짐작으로 숫자를 바꾸지 않는다. 과거 30경기에서는 `speed`가 `0.87`
근처의 계단처럼 보였지만, 각 값 200경기 스윕에서는 가장 큰 인접 변화가
8.5%p였고 모든 인접 신뢰구간이 겹쳤다. 작은 표본의 급변을 임계점으로
확정하지 않고 구현 단계가 끝날 때 같은 스윕을 반복한다.

측정은 `tools/soccer-sim.js` 로 한다. `readHuman` 만 봇으로 갈아끼우고
실제 `step(1/60)` 을 반복 호출한다.

```bash
node tools/soccer-sim.js -n 200
```

브라우저 `requestAnimationFrame` 에 의존하지 않는다 — 백그라운드 창에서
초당 1회로 스로틀된다.

**표본 수를 함께 보고한다.** 30경기의 승률은 95% 신뢰구간이 ±18%p 라
난이도 간 차이를 판정하기에 부족하다. 밸런스를 바꿀 때는 200경기 이상을
쓴다.

## 검증

코드만 읽고 "될 것" 이라고 판단하지 않는다. 로컬 서버로 실제로 연다.

```bash
python -m http.server 8899   # 끝나면 프로세스를 정리한다
```

데스크톱·태블릿·모바일 크기와 세로 화면을 함께 본다.

### 연습 모드

혼자 조작을 시험할 때 쓴다. 제목 화면의 **「연습 모드」 버튼**으로만
켜진다. 누르면 나머지 21명이 구석으로 치워지고 시계가 멈춘다.
좌하단에 공 높이·접촉 구간·속도·체력·충전이 실시간으로 뜬다.

기본 조작은 아래 「키 배치」와 같고, 여기에 연습 전용 키가 더해진다.

| 키 | 동작 |
|---|---|
| `B` / `1` | 공을 발밑에 리셋 (**소유까지 준다**) |
| `2` `3` `4` | 공을 0.75m(가슴) / 1.8m(헤딩) / 4m(무접촉) 높이에 띄움 |
| `V` | 공 정지 |
| `G` / `T` | 상대 골키퍼 / 상대 선수 1명 토글 |
| `H` | 도움말 줄 토글 |
| `Esc` | 연습 모드 종료 (제목 화면으로) |

**공을 소유하지 않으면 패스·슛은 아무 반응이 없다.** 접촉 반경이
`R_PLAYER + R_BALL` = 8.2단위(0.41m)뿐이라, 공을 앞에 놓기만 하면 손이
닿지 않는다. 지면 리셋(`B`/`1`)이 소유까지 주는 이유가 그것이다.
공중 리셋(`2`~`4`)은 자유공이어야 튕김·헤딩을 볼 수 있으므로 소유를
주지 않는다 — 이때 패스가 안 먹는 것은 정상이다.

### 키 배치 (2026-08-03)

**2인 대전은 없앴다.** 조작은 1P 하나뿐이다.

| 키 | 동작 |
|---|---|
| `WASD` / 방향키 | 이동·조준 |
| `;` | 스프린트 |
| `'` | 걷기 |
| `Enter` | 슛 (공이 없으면 태클). 누른 길이가 세기·높이 |
| `\` | 패스. **항상 땅볼**이고 누른 길이가 거리를 정한다 (19~54m) |
| `]` | 스루패스 |
| `[` | 선수 전환 |

**`Shift` 는 쓰지 않는다.** Windows 고정 키가 Shift 5회 연타를 가로채
안내창을 띄우고 브라우저 포커스를 뺏는다. 패스처럼 연타하는 키를 Shift 에
두면 몇 초 만에 걸린다. `Ctrl`·`Alt` 도 같은 이유로 피한다.

이 함정은 브라우저 자동 검증으로 잡히지 않는다 — CDP 로 넣는 키는
Windows 접근성 계층을 건너뛰기 때문이다. **실제 키보드로 눌러봐야
드러난다.**

슛과 패스의 충전 시간 기준이 다르다 — 슛은 `shootCharge` 가 `dt` 로
쌓이고, 패스·스루는 `holdStart` 가 `performance.now()` 를 쓴다. 실제
플레이에서는 둘이 같이 흐르지만, **`step()` 을 동기로 반복하는 검증
코드에서는 벽시계가 진행하지 않아 패스 충전이 항상 0 이 된다.**
패스 충전을 시험하려면 실제 시간을 두고 눌러야 한다.

`solo` 플래그가 꺼져 있으면 키 처리도 `soloTick()` 도 즉시 빠져나간다.
URL 파라미터로는 켤 수 없다 — 버튼이 유일한 진입점이다.

### 기능 실측 `tools/soccer-lab.js`

브라우저 없이 선수 1명을 격리해 수치를 뽑는다. 통합 측정으로는 안 보이는
개별 기능의 동작을 본다.

```bash
node tools/soccer-lab.js          # 8구간 전부
node tools/soccer-lab.js gk       # 한 구간만
node tools/soccer-lab.js --list
```
